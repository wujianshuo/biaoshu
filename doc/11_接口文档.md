# 第一阶段接口

API 根路径 `/v1`。请求头 `Authorization: Bearer <token>`。服务根据令牌识别租户、账号、角色和允许访问的项目。请求体中的项目 ID 只用于定位，权限由后端判断。登录后工作台通过同源 API 操作。

## 项目、文件和版本

| 方法和路径 | 参数和结果 |
| --- | --- |
| `GET /v1/projects` | 令牌可访问的项目 |
| `POST /v1/projects` | `project_name`，可选 `industry`、`specialty`、`region` |
| `POST /v1/projects/{id}/documents` | multipart `file`，可选 `category`。更新已有文件时附 `document_id`、`expected_revision` |
| `GET /v1/projects/{id}/records/{kind}` | 当前各业务记录 |
| `GET /v1/projects/{id}/records/{kind}/{key}` | 记录字段及 `revision`，可选 `?revision=N` 查询历史 |
| `GET /v1/projects/{id}/records/{kind}/{key}/versions` | 版本链、创建人、内容摘要 |
| `GET /v1/projects/{id}/documents/{key}/download` | 原始文件，可按历史版本下载 |
| `GET /v1/projects/{id}/artifacts/{key}/download` | Excel、Word 或 PDF。审核稿每次下载复核输入有效性 |
| `GET /v1/projects/{id}/technical-plan` | 已确认输入对应的技术标目录、逐章条款和评分 ID |
| `GET /v1/projects/{id}/analysis-sources` | 当前确认档案的原文片段和来源 ID，可分页 |
| `PUT /v1/projects/{id}/analysis` | 人工修订解析。提交 `revision`、`note`、`items` 和可选 `remove_ids`。新增项的参数与 WF02 提示词一致 |
| `PUT /v1/projects/{id}/chapters/{key}` | 提交 `revision`、`content`、`note`，可带待确认项和本章确已响应的条款、评分 ID |

`category` 支持 `tender`、`amendment`、`drawing`、`boq`、`template`、`other`。自动识别以文件名和格式为依据，重要资料应显式指定类别。

## 工作流

统一 `POST /v1/workflows/{WF}/run`，请求为 JSON，`project_id` 表示项目。WF01 创建新项目时可留空并提供项目名。Dify 传入 `request_json` 与开始节点的 `project_id`。

| 编号 | 特有输入 | 主要记录与产物 |
| --- | --- | --- |
| WF01 | `project_name`、`industry`、`document_ids` 可选 | `archive/latest` |
| WF02 | `document_ids` 可选，须包含所有确认的正文与补遗 | `analysis/latest` |
| WF03 | 经确认的当前解析结果 | `requirement/latest`、`requirements` XLSX |
| WF04 | 经确认的当前解析结果 | `score/latest`、`scores` XLSX |
| WF05 | 可选 `as_of` | `match/latest`、`evidence-matches` XLSX，候选资料和来源版本 |
| WF06 | 可选 `chapter_ids` | `chapter/CH-xx`，独立章节 DOCX 和编制依据 |
| WF09 | 当前技术章 | `audit/latest`、`review-report` XLSX |
| WF10 | `mode=draft\|reviewed`，可选 `template_document_id`、`include_pdf` | 技术标草稿或审核稿。默认 DOCX |

WF01 另外支持 `POST /v1/workflows/WF01/upload`。multipart 字段为 `project_id`、`request_json` 与可重复的 `files`。可在 `request_json` 里通过 `document_kinds` 指定 `{"招标.pdf":"tender","补遗.pdf":"amendment"}`。若一项解析失败，错误响应会列出已保存的项目和资料，便于从同一项目补传。

成功工作流响应通常包含 `project_id`、`workflow`、`run_id`、`status` 和记录/文件键。HTTP 409 表示缺前置确认、版本变化或存在待处理冲突。HTTP 422 表示参数或可追溯来源问题。模型未配置、连接异常或输出无效返回 503/502。

## 复核

`POST /v1/projects/{id}/records/{kind}/{key}/review`。仅复核或管理角色可用，需不同于目标记录编制人。示例 `{"revision":1,"decision":"approve","note":"已查招标原文","resolutions":{}}`。

- 档案遇到低质量文本时，`resolutions.parse_confirmations` 逐份填写 `document_id@revision`。正文、补遗毫无可用文本需补件后重跑。
- 解析报告有补遗时设置 `amendments_reviewed:true`。人工确认的修改关系为 `supersessions:[{"old_id":"REQ-旧","new_id":"REQ-新"}]`。事实仍有歧义时，用 `fact_choices` 显式选源。曾剔除不可核验的模型条目时，需要核对后设置 `sources_reviewed:true`。
- 企业匹配报告用 `evidence_decisions` 指定各项 `accepted`、`pending` 或 `missing`，采纳时选择 `candidate_keys` 里的版本。工期等关键值、引用版本和证据失效继续由 WF09 校验。
- 审核稿要求当前章节、审查报告和草稿都已复核。先输出草稿并检查实际 Word 版式后，再由复核账号确认草稿版本。

## 知识和企业证据

企业资料接口使用具备企业库权限的账号。以 `/v1/knowledge/{key}/versions` 创建与列出资料版本。对 `/{version}/review` 提交发布、退回或停用决定，参见知识库文档。本地向量模型配置后，登记分块时可用 `build_embeddings:true` 构建嵌入。知识检索用 `POST /v1/knowledge/search`，请求 `query` 和可选 `filters`、`query_vector`、`embedding_model`。WF06 自动选同专业、适用且已生效的可引用版本。

结构化证据通过 `GET /v1/evidence`、`POST /v1/evidence/{key}/versions` 和 `POST /v1/evidence/{key}/versions/{version}/review` 管理。来源字段记录原件定位，首阶段证据包的业务输出为有版本的引用与核验结果。

`POST /v1/knowledge/{key}/ingest` 接收到内网的原件并计算实际 SHA-256。multipart 包含 `file` 与 `metadata_json`，后者至少含 `title`、`category`、`source`、`source_version`。初版自动按解析器的来源位置切片，保存原件并登记为待审核。原件用 `GET /v1/knowledge/{key}/versions/{version}/original` 鉴权读取。外部企业资料系统的原件也可用来源与摘要登记，复核人从已登记位置核实。
