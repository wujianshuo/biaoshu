# 系统测试与阶段验收

以项目为单位验证 WF01–WF06、WF09–WF10。每次记录代码版本、数据库引擎、Dify 版本、模型标识、测试数据来源和实际结果。当前阶段的执行情况见 [项目实施进度](12_项目实施进度.md)。

## 本地自动验证

```shell
python -m unittest discover -s tests -v
python scripts/dify_workflows.py --check
python scripts/verify_dify_workflows.py
python scripts/verify_dify_native_schema.py <本地Dify-1.7.2源码目录>
```

测试分为以下几层。

| 层 | 覆盖 |
| --- | --- |
| 文件解析与导出 | PDF 页码、条款原文、有线框表格，DOCX 标题和表格顺序，XLSX 全工作表、坐标、公式与前导零，扫描或 CAD 的状态，Word 目录和页码域，XLSX 保留原文并阻止其作为公式执行。 |
| 业务存储和知识 | 相同项目 ID 在不同租户间隔离，项目版本冲突可识别，记录可追溯。知识检索排除未审核、已停用或不适用的条目，并能返回来源、版本和审核者。使用新版替代历史材料后复查历史可追溯性和当前检索结果。 |
| 业务 API | 通过本机回环 HTTP、测试数据库和合成招标资料跑八条流程。使用不同编辑和审核账号。核对文件版本、失效审批、补遗处理、响应表和评分表内容、章节依据、审查结果和 Word 下载。对无权限访问、旧版审核、必填材料缺失和下载无权限分别核对状态码。 |
| Dify DSL | 八份 YAML 由生成器重现，独立解析并检查节点、变量选择器、分支和终止节点。检查业务 API 的 JSON 请求和 WF01 multipart 的请求结构。 |

自动化测试使用测试令牌、临时文件目录和合成资料。模型测试替身仅用于稳定覆盖输入输出、证据引用和异常路径。数据库使用 SQLite 的本地测试需要另做 PostgreSQL 迁移和运行验证。

## 真实 Dify 验收

1. 在隔离的 Dify 工作区导入 `workflows/` 下的八份 DSL，每份记录是否导入成功、显示的 Dify 版本和失败消息。
2. 配置业务 API 基址和测试凭证，验证 Dify HTTP 节点能访问内网 API。逐个在编辑器试跑，保留 Dify 执行 ID、返回状态和后端记录引用。
3. 使用同一个测试项目运行顺序 `WF01 → 审核 → WF02 → 审核 → WF03/WF04 → WF05 → WF06 → 审核 → WF09 → WF10`。按需核准企业资料匹配、审查报告和技术标草稿。
4. 核对 WF01 的本地文件上传及 JSON 运行分支。对 WF06 限定单章重跑，确认未选择的章节没有新增版本。核对 WF10 的 Word 能被读取，打开后更新目录域，检查封面、页码和表格。
5. 审核各节点的 `status` 和 `http_status`。Dify 执行成功时，后端仍可能返回待复核状态、输入错误或权限错误。按业务状态判断结果。

## 阶段业务验收

选择一套授权使用的真实工程招标资料，要求包含招标正文和适用补遗。由编标人先标注关键条款、评分标准和引用位置。使用本地模型实际执行，按标注核对实质性条款漏检、关键值错填、定位准确性、证据缺项提示和人工复核用时。

关键检查包括确认后的工期、质量、施工范围能追溯原文，补遗替换关系保留审查记录，章节引用可定位至明确版本。下游产物遇到上游版本变更时要求重新生成或审核。真实 OCR 准确性、PDF 转换效果、企业模板排版和当地交易平台提交要求应逐项目验证。
