# 部署与运维

## 准备

- Python 3.12 用于初始化配置、离线测试和验收脚本。
- 本项目 Compose 启动 API 和独立 PostgreSQL 16。数据库端口只在本项目网络内可见。API 默认绑定宿主机 `127.0.0.1:8091`。第一阶段配置不会改动现有 Dify 服务。
- 已有企业 Dify 需要可用的代码沙箱以及 HTTP 请求节点。代码按 1.7.2 官方模型做兼容校验。部署前记录实际版本并逐条导入。
- 对话模型应提供内网 OpenAI 兼容 `/v1/chat/completions`。如果配置嵌入模型，使用同一接口根的 `/v1/embeddings`。后端核验地址是内网或回环地址，直连已核验地址，不跟随重定向。
- 文件解析和 Word/Excel 生成在同一后端进程的独立格式模块执行。文本 PDF、DOCX、XLSX、TXT 可直接验证。OCR 和 PDF 导出是可选运行时组件。

[Dify 自部署文档](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose)

## 启动后端

```powershell
python scripts/init_environment.py
docker compose config --quiet
docker compose up -d --build
docker compose ps
Invoke-RestMethod 'http://127.0.0.1:8091/healthz'
```

初始化脚本为编制、复核角色分别生成随机令牌，并生成随机数据库密码。`.env` 只在部署机保存。首次启动会执行 `db/001_schema.sql`、`db/002_seed.sql`。应用启动还会核对并幂等初始化数据库。已有部署先备份，按版本维护迁移记录。

若模型服务部署在 Windows 宿主机且能从 Docker 网络访问，可在 `.env` 使用 `BIAOSHU_MODEL_BASE_URL=http://host.docker.internal:11434/v1`。按实际部署填写模型名。局域网部署使用企业内网地址。确认模型路径支持 JSON 正文并有合适的上下文、输出额度。修改后 `docker compose up -d api`。模型未配置时，可先使用项目、资料入库和知识库接口，WF02/WF06 将返回明确的服务配置提示。

本机暂时无法运行 Docker 时，可用 Python 3.12 安装 `requirements-test.txt`，生成 `.env` 后执行 `python scripts/run_local.py`。默认创建 `data/local.sqlite3` 并仅监听回环地址。也可以在 `.env` 配置已运行的 PostgreSQL DSN 进行同样的调试。该入口供本机验证和排障使用。

## Dify 接入

若已有内网 TLS 网关发布 API，设置 `BIAOSHU_API_BASE` 为 Dify 的 HTTP 请求节点可到达的网关根地址。若同台 Docker 用网络连接，可由运维创建专用网段并使用 `deploy/compose.dify-network.yml`。

```powershell
docker network create biaoshu-dify
docker compose -f compose.yml -f deploy/compose.dify-network.yml up -d --build
```

在 Dify 的部署配置中，将执行 HTTP 请求的服务和实际使用的 HTTP 代理接入同一专用网络。网关或代理仅为所需的业务 API 地址配置内网访问。Docker 网络别名为 `biaoshu-api`，Dify 的环境变量可设为 `http://biaoshu-api:8091`，以实际路由和代理设置为准。导入各 DSL 后设 Secret `BIAOSHU_API_TOKEN` 为拥有目标项目权限的编制凭证，由独立复核凭证处理审核。

WF02 和 WF06 可能超过默认代理或 Dify HTTP 节点时限。先用小样验证，长文件分批确认。WF06 可按 `chapter_ids` 分章调用。调整限额时核对 Dify 对应版本支持的读取时限、Dify 前置代理以及模型本身的请求超时。

[Dify 环境配置文档](https://docs.dify.ai/en/self-host/deploy/configuration/environments)

## 文件存储和格式

默认使用 Docker 持久卷，按租户与项目命名空间和文件 SHA-256 存储。PostgreSQL 记录原文件名、相对版本、有效引用和摘要。下载走同一授权 API。

如使用现有内网 MinIO 或 S3 兼容服务，配置 `BIAOSHU_STORAGE_BACKEND=s3`、`BIAOSHU_S3_ENDPOINT`、`BIAOSHU_S3_BUCKET`、`BIAOSHU_S3_ACCESS_KEY`、`BIAOSHU_S3_SECRET_KEY`。存储桶需要预创建、保持私有。应用凭证授予该桶所需的读写、列表与桶策略读取权限。首次切换存储时迁移源文件并核对摘要，保留数据库与原件的一致备份。

OCR 可配置 `BIAOSHU_WITH_OCR=1`、`BIAOSHU_OCR_BIN=/usr/bin/tesseract`。使用 `chi_sim+eng` 语言包。OCR 识别结果必须在档案里逐份确认。可选 PDF 转换配置 `BIAOSHU_WITH_PDF_EXPORT=1`、`BIAOSHU_SOFFICE_BIN=/usr/bin/libreoffice`，重新构建镜像后在 WF10 使用 `include_pdf=true`。工程专用 CAD 和旧版二进制 Office 文件，先用企业现有工具输出可校对的 PDF 或 Office 文件，再按源文件登记。

## 备份、恢复与审计

1. 在维护窗口停止写入，保持 PostgreSQL 与对象文件一致。备份 SQL 快照和对象数据，同时记下镜像版本、工作流和模板版本。令牌与密码走企业独立密码库。
2. PostgreSQL 示例先在容器内执行 `docker compose exec postgres pg_dump -U biaoshu -Fc -f /tmp/biaoshu.dump biaoshu`，再使用 `docker compose cp postgres:/tmp/biaoshu.dump ./backup/biaoshu.dump`。文件卷使用企业 Docker 卷备份流程，内网 S3 配置版本保留和私有备份。
3. 在新数据库、新卷或新桶恢复，使用当前部署的初始化 SQL 补齐必要对象，然后检查项目隔离、原件 SHA-256、版本链、知识发布状态及一轮草稿导出。
4. 项目运行与材料读取有审计记录。应用日志只记录工作流、项目编号、运行编号、状态和调用者标识。需要排查时用编号查工作台和 Dify 日志。请按企业制度设置留存、备份密级和传输权限。
